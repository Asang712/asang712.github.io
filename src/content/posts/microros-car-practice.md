# 从建图失败到视觉伺服：一台 MicroROS 小车的踩坑记录

## 写在前面

过去几天我一直在折腾一台 MicroROS 小车：ESP32 控制板跑 micro-ROS，电脑端跑 ROS 2 Jazzy，通过 UDP 连接 Agent，配一个 HTTP MJPEG 相机，再用手机 App 通过 rosbridge 遥控。

目标本来很朴素：让它建个图、自己导航。结果真正花时间的既不是 SLAM 算法，也不是路径规划；问题主要出在链路、QoS、生命周期状态这类容易被忽略的地方。这篇文章按时间顺序记录这条链路如何一步步跑通，中间踩了哪些坑，以及最后为什么决定放弃建图，转向视觉伺服。

## 一、先让链路活下来

系统大概长这样：

```
手机 App ──WebSocket(9090)──> rosbridge ──> ROS 2 话题
                                            │
ESP32 控制板 ──UDP(8090)──> micro-ROS Agent ─┘
HTTP MJPEG 相机 ──> camera_driver ──> /camera/image_raw
```

最开始遇到的第一个问题是**话题突然全没了**。排查下来不是代码问题，而是链路上几个物理层细节：

- micro-ROS Agent 是前台进程，关掉终端它就没了；
- 控制板和电脑必须在同一网段，能互相 ping 通；
- 手机热点重启后 DHCP 会重新分配地址，昨天的 IP 今天就不对了；
- USB 线插在控制板上时，固件会切到 USB HID 手柄模式，此时 `/cmd_vel` 完全无效；
- 电池电压低于 6.5 V 时，控制板会挂起 Wi-Fi、串口等模块，表现是“配置写入超时”。

这些问题有一个共同点：**ROS 层面的日志完全正常**，你只能从系统层面找原因。后来我养成了一个习惯——先确认物理链路，再看 ROS。

## 二、QoS：最沉默的故障

链路通了以后，相机画面出不来。发布端有数据，订阅端也在，但就是收不到。

原因是 QoS 不匹配。micro-ROS 端发布 `/scan` 和图像用的是 `BEST_EFFORT`，而我在订阅端写的是 `RELIABLE`。ROS 2 不会因为 QoS 不兼容而报错，只会静默地一帧都不给你。

修法很简单，两端统一：

```python
self.create_subscription(
    Image,
    '/camera/image_raw',
    self.image_callback,
    rclpy.qos.QoSProfile(
        depth=10,
        reliability=rclpy.qos.ReliabilityPolicy.BEST_EFFORT,
    ),
)
```

排查命令值得记下来：

```bash
ros2 topic info /scan --verbose   # 看 Publisher 和 Subscription 各自的 Reliability
```

**教训：在 ROS 2 里，“没有数据”要先怀疑 QoS，再怀疑代码。**

## 三、SLAM 不工作，也不是算法问题

建图时另一个诡异现象：`slam_toolbox` 进程活着，日志只有一行 `Node using stack size`，然后再无输出。

一开始我按 QoS 思路排查，但 `ros2 node info /slam_toolbox` 给出了答案：

```
Subscribers:
  /parameter_events   ← 只有这个，没有 /scan
```

原因是 `slam_toolbox` 是**生命周期节点**。手动 `ros2 run` 启动时它停在 `unconfigured` 状态，`/scan` 订阅是在 `on_configure` 里才创建的。厂家 launch 能跑，是因为 launch 带了生命周期管理。

手动补两条命令即可：

```bash
ros2 lifecycle set /slam_toolbox configure
ros2 lifecycle set /slam_toolbox activate
```

之后 `/map` 以约 1 Hz 正常输出。

**教训：lifecycle 节点的“进程活着”不等于“节点在工作”。**

## 四、一张看不懂的地图

SLAM 跑起来了，但建出来的图是这样的：中心一个半径约 2 米的白色实心圆，外围是放射状星芒，黑点零散分布，没有连续墙面。

这是典型的**扫描帧没有被放到正确位姿**——所有帧都叠在原点反复叠加。正常情况下应该检查三件事：

1. `/odom_raw` 的 `x/y/yaw` 是否随车移动而变化；
2. `/scan` 的 `ranges` 是真实距离，还是大量 `inf`；
3. `tf2_echo map base_footprint` 是否随车变化。

这里还有一个值得记录的教训：我当时根据记忆里的参数推断“白圆半径 2 米，正好等于 `max_laser_range`”，但仓库里的实际配置是 `12.0`，不是 `2.0`。**不要凭记忆推断运行时参数**，查当前值要用：

```bash
ros2 param get /slam_toolbox max_laser_range
```

另外，如果同时跑了 `slam_toolbox` 和自定义位姿桥接节点，两者可能同时发布 `map→odom`，导致 TF 互相覆盖。建图时应该只保留一个发布者。

## 五、决定：不建图也能导航

建图排查到一半，我重新评估了需求：我真正想要的是“车能找到东西、能靠近”，而不是“拥有一张完整地图”。

于是把方案改成了**无地图导航（mapless navigation）**。常见路线有四条：

| 路线 | 原理 | 适用场景 |
|---|---|---|
| 视觉伺服 | 检测到目标就转向靠近 | 单房间找东西、跟人 |
| 示教复现 | 手动走一遍录制里程计，之后回放 | 固定短路线送物 |
| 视觉路标 | 在关键位置贴 AprilTag/二维码 | 跨房间、多区域 |
| 巡线 | 沿地面色带走 | 展馆、产线 |

最终选的是**视觉伺服 + 语音指令**：说一句“帮我找红色水杯”，车原地转着扫描，检测到目标就靠近，框足够大就停下。

## 六、视觉伺服到底是什么

一句话：**边看边走，看偏了就修。**

它不是“识别一次 → 算出坐标 → 开环冲过去”，而是把图像中的偏差直接当作控制反馈：

```
期望目标 → 视觉伺服控制器 → 底盘/云台运动
                ↑                    ↓
            检测与误差 ←──── 相机成像
```

核心映射只有三条：

| 图像量 | 控制量 |
|---|---|
| 目标框中心的水平偏移 | 角速度 ω |
| 目标框面积 | 前进速度 v |
| 居中且框面积超过阈值 | 停车 |

这种做法的好处是**完全不需要地图和全局定位**，容错性也强。但它有三个现实问题：

- **目标丢失**：必须设计扫描策略，不能默认目标一直在画面里；
- **帧率与延迟**：实测相机链路只有 2.5～4 Hz，伺服会一顿一顿，甚至来回振荡；
- **尺度不确定**：框面积只是距离的近似，不同目标要分别设阈值。

所以下一步真正要解决的，是帧率，而不是算法。

## 七、语音：先别急着买硬件

我一开始以为要在车上加麦克风模块。核对后发现，小车控制板只有蜂鸣器，根本没有音频输入；而作为上位机的笔记本自带麦克风，`arecord` 和 PipeWire 都能直接用。

也就是说，语音链路的正确位置是**电脑端**：

```
电脑麦克风 → 录音(16 kHz) → 语音转文字 → 文本 → 大模型 → 动作指令
```

识别可以走云端 Dify 接口，也可以本地跑 `whisper.cpp` 或 `vosk`，完全离线。小车只负责执行 ROS 2 指令，一行固件都不用改。

## 八、把流程工程化

调试稳定后，我把散落在各个终端里的命令收成了一个脚本，一条命令拉起三条链路：

```bash
./start_nomap.sh --check   # 环境自检
./start_nomap.sh           # Agent + 主系统 + 位姿桥接
```

它解决了几个容易忘记的问题：

- `bringup_app` 默认会启动 SLAM，不建图时必须显式传入 `slam_mode:=none`；
- launch 读取固定路径下的 `robot_info.json`，文件不存在会直接抛 `FileNotFoundError`；
- 子进程用 `setsid` 独立成组，退出时按进程组关闭，否则 `ros2 launch` 的子节点会残留；
- `source setup.bash` 时 ROS 引用了未定义变量，需要临时关闭 `set -u`。

脚本退出后会验证没有残留进程，这一点比“能启动”更重要。

## 九、复盘

回头看，这个项目里真正难的从来不是算法：

1. **物理层和中间件层占了大部分时间**——IP、电压、USB 模式、QoS、生命周期；
2. **“没有报错”不等于“工作正常”**——QoS 不匹配、lifecycle 未激活都是静默失败；
3. **需求比技术重要**——放弃建图之后，方案一下子简单了许多；
4. **参数要查，不要猜**——仓库配置和运行时值可能不一致；
5. **先让链路可重复启动，再谈功能**。

下一步的计划是把视觉伺服真正写出来：搜索状态机、误差到速度的映射、到位判定，然后把语音接进来。如果顺利，这台小车就能听懂一句“帮我找一下红色水杯”，然后自己转过去。
